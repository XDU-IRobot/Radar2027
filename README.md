# Radar

Radar 是 RoboMaster 雷达站通信项目，负责接收裁判系统数据、维护比赛状态，并按规则生成和发送雷达相关指令。项目主线是“接收、处理、发送”，不包含视觉识别功能。

## 赛场角色与核心任务

### 规则影响与定位依据

2027 赛季通信协议将雷达站纳入裁判系统的状态感知和指令交互链路。首先，`0x020E` 雷达自主决策信息提供双倍易伤机会、敌方双倍易伤状态、己方加密等级和密钥修改权限等状态量，雷达站可以据此判断是否具备发起相应策略的条件。其次，`0x0121 RadarCMD` 为雷达向裁判系统提交自主决策的专用指令，承载双倍易伤请求和己方密钥更新等动作；2027 版本新增的装甲加固字段暂不因字段存在而自动触发，避免把协议解析误当成战术决策。再次，信息波中的 `0x0A01` 与队友位置数据共同构成小地图更新来源，项目通过 `0x0305` 向己方选手端转发有效的己方机器人位置。敌方密钥链路 `8002/8003` 及其 `0x0A06` 帧，则使雷达站能够接收并校验敌方密钥相关信息。

因此，本项目在赛场上的定位是“裁判系统数据汇聚、状态判断和战术指令执行节点”。它不承担相机目标检测或直接操控机器人，而是把分散在串口和多条 TCP 链路中的规则状态转换成可靠、及时、可追溯的队伍态势信息和裁判系统指令。这个判断的思路是：先按规则确定雷达可获得的状态和可提交的动作，再检查项目实际拥有的输入、决策、发送和日志链路，最后将两者的交集确定为项目边界。

### 比赛各时段的主要任务

在比赛开始前，雷达站主要完成链路和协议准备：确认串口及 `8001/8002/8003` TCP 通道可用，校验协议帧和 CRC，建立初始状态，并检查发送调度和日志是否正常。此阶段的重点是让比赛中的输入、状态和发送路径处于可观测的工作状态。

比赛进行中，雷达站持续接收裁判系统常规协议、信息波和敌方密钥数据，维护比赛阶段、己方机器人位置、雷达自主决策状态和密钥状态。对于位置数据，及时过滤无效或过期信息并发送 `0x0305`，为己方提供小地图态势；对于 `0x020E`，根据剩余机会、敌方状态和密钥权限生成 `0x0121`，在满足规则条件时提交双倍易伤或己方密钥更新请求；对于敌方密钥，则完成接收、校验和转交。所有发送动作经过统一节流、冷却和队列调度，避免因重复触发或链路抖动造成无效指令。

比赛后段和结束阶段，雷达站重点处理有限机会的使用和状态收尾：在仍有规则机会且条件满足时完成必要的最后一次策略请求，避免重复消耗；比赛结束或输入超时后停止依据陈旧状态作出新的决策，同时保留原始字节流、结构体状态、连接变化和发送结果，支持赛后复盘和故障定位。

### 关键能力与后续需求依据

上述定位要求项目具备四类核心能力。第一是多链路可靠接入能力，包括串口和 TCP 的非阻塞接收、自动重连、空闲超时处理、独立回放和逐帧协议校验。第二是规则状态建模能力，需要按协议版本正确解析 `0x0001`、`0x020E`、`0x0A01`、`0x0A06` 等数据，区分有效、过期和保留字段，并维护跨帧状态。第三是受约束的决策与发送能力，需要把规则条件映射为 `0x0121` 和 `0x0305`，实现冷却、去重、重发、优先级和发送节奏控制，确保动作可执行且不会因重复发送失真。第四是可观测和可恢复能力，需要保留原始数据与关键决策证据，记录链路状态和运行指标，并支持文件回放，以便在无现场设备时复现问题。

这些能力直接构成后续功能需求的依据：新增规则字段应先进入版本隔离的状态模型和日志，再决定是否接入策略；新增战术动作应通过统一发送调度器提交；任何依赖实时状态的功能都必须定义超时、失联和重复触发行为。这样可以保持雷达站作为通信和决策节点的战术定位，并将规则变化转换为可验证的软件需求。

## 主要功能

- 通过串口接收裁判系统常规协议。
- 通过 TCP 接收信息波和敌方密钥链路数据。
- 支持真实设备输入和二进制文件回放。
- 根据比赛状态维护并发送 `0x0305` 小地图数据，以及 `0x0301/0x0121` 雷达指令。
- 记录协议数据、原始字节流和运行状态，便于调试与赛后复盘。

当前配置使用 RoboMaster 2027 V1.0.0 通信协议。协议版本、输入模式和链路参数统一在 [include/config/config.hpp](include/config/config.hpp) 中配置。

## 构建

```bash
cmake -S . -B build
cmake --build build --target radar -j2
```
